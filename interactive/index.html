01

La cita la confirma Hermes

Ingenius 360 atiende la agenda clínica con una máquina de estados. El paciente pide, verifica y deja una solicitud. Hermes es quien confirma, reprograma o cancela la cita en firme. Este servicio origina la solicitud y el pre-registro, y ahí se detiene.

Cada frase sale de la configuración del tenant, de su base de conocimiento o de los datos de dominio. El recorrido es determinista: el mismo paso, con los mismos datos, produce la misma respuesta.

En el repositorio conviven dos piezas que en producción se separan. El chatbot se despliega. El simulador de Hermes se apaga. El chatbot solo usa del simulador lo que Hermes ofrece por FHIR.

02

El turno es un paso

El motor guarda un paso y un contexto. El paso dice qué puede ocurrir ahora. El contexto conserva lo justo para seguir: el documento, el borrador del pre-registro, la cita elegida. La respuesta de verificación y el dato clínico no se escriben en el mensaje, ni en la auditoría, ni en el log.

El recorrido real pasa por el menú, el tipo y el número de documento, y una verificación con un par fijo de preguntas. Si la verificación falla, el paso queda bloqueado. Si la persona no está en el padrón, lee el aviso de privacidad y completa el pre-registro campo a campo. Para una cita elige servicio, profesional, día, cupo y confirmación. Desde el menú también consulta la base de conocimiento o pide un asesor. Cancelar y reprogramar parten de una cita ya elegida.

El mismo widget tiene tres montajes. Los tres hablan directo con el backend por CORS. El origen permitido se administra en la pantalla Bot.

Script Corre en el sitio del tenant. Ese origen es el que ve el backend.
Iframe La página /widget. El origen es el del frontend.
Consola La ruta /chat, también con el origen del frontend. 
<script src="https://<frontend>/widget.js"
  data-key="<clave>"
  data-api="https://<backend>" async></script>

03

Un hueco, una transacción

Agendar o reprogramar no confirma la cita. Aparta un cupo. El estado pasa de free a busy_tentative dentro de la misma transacción. Si dos solicitudes llegan a la vez, una se queda con el hueco y la otra sigue sin él.

El apartado vence. El vencimiento se evalúa al leer, también cuando Hermes lee Slot, Appointment o Task. Un barrido periódico recoge lo que nadie volvió a mirar. Hay un tope de solicitudes pendientes por paciente, para que nadie acapare la agenda.

Toda escritura acepta Idempotency-Key persistida en la base. Repetir la misma petición devuelve el mismo resultado y no abre una segunda solicitud.

04

Las dependencias apuntan hacia adentro

Cada contexto de negocio vive en modules/<contexto> con tres capas. domain define entidades y puertos. application orquesta casos de uso a través de esos puertos. infrastructure los cumple: Prisma, el reloj, los identificadores, el HTTP que sale.

domain y application no importan Next, Prisma ni node:. Lo cierran dos mecanismos a la vez: la regla noRestrictedImports de Biome y la suite fronteras. Si algo hace entrada-salida, vive en infraestructura, aunque el archivo que lo llama no abra un socket.

composition-root.ts es el único sitio que une un adaptador concreto con un caso de uso. Los route handlers de src/app/ validan, autentican, traducen el error y delegan. Cuando un handler crece más que eso, falta un caso de uso.

El frontend no repite reglas de negocio. Consume el cliente generado desde OpenAPI y ese cliente no se edita a mano. La validación de forma —campo vacío, formato— sí vive en la interfaz. La de negocio, no.

La skill de arquitectura hexagonal llama adapters a la capa de afuera. En este repositorio esa capa se llama infrastructure. La gobernanza gana el conflicto.

05

Un dominio, dos errores distintos

El mismo núcleo tiene dos puertas HTTP. Cada una habla el contrato de quien la llama. Las envolturas no se cruzan.

REST /api/v1 para el widget, el panel y el chat. El fallo llega como { error: { code, message, request_id, details } } con la cabecera X-Request-Id. Si el cliente manda ese id, vuelve el mismo.
FHIR /fhir para Hermes. El fallo es un OperationOutcome con application/fhir+json.
Plataforma /api/platform/v1 da de alta tenants y emite tokens. Usa la envoltura REST y el secreto de plataforma.

GET /fhir/metadata declara exactamente lo implementado. Los recursos de escritura condicional son Patient, Practitioner, HealthcareService, Schedule y Slot. La pre-agenda viaja como Appointment en estado proposed. La cancelación viaja como Task. El pre-registro es un Patient con la etiqueta pre-registered. Perfiles y constantes viven en un solo módulo. Dos mappers parecidos, de recursos distintos, siguen separados.

El tenant sale solo del claim del JWT. Los roles son widget, operator, admin y service. Un recurso de otro tenant responde 404: desde fuera, la ausencia y el acceso ajeno se ven igual. El rol widget alcanza únicamente el chat de su sesión. Las escrituras FHIR quedan para el rol service, y la auditoría las anota como escritas por Hermes.

06

Cinco fases, en ese orden

No se abría la siguiente sin cerrar los criterios de la anterior. El stack del primer día es el que quedó: Next.js con App Router, Prisma y Postgres. Biome, Vitest y React Doctor vigilan cada cambio. Hay dos package.json a propósito, sin workspaces de npm: la raíz solo orquesta. Docker multi-stage levanta Postgres, el backend y el frontend. process.env se lee en un solo módulo de configuración por proyecto.

  1. 1
    Cimientos. Monorepo, hexágono vacío, JWT, contrato REST mínimo, Docker, CI y gobernanza.
  2. 2
    Dominio. Agenda, historial y ajustes detrás de puertos. Seed simétrico de dos tenants, con el simulador en el esquema hermes_sim. El panel llama al cliente generado.
  3. 3
    Chat. Sesión del widget, motor determinista, verificación, pre-agenda, base de conocimiento, bandeja y idempotencia en base de datos.
  4. 4
    FHIR. Lectura y escritura condicional. El simulador cierra el ciclo —maestros, pre-agendas, pre-registro— solo por FHIR, con token service.
  5. 5
    Entrega. Límites de tasa en un store compartido, tickets de asesor en el panel, barrido de apartados, secretos fuera del compose, colección Postman y la suite carga-basica.
  • Complejidad cognitiva de una función, hasta 15
  • Una función, hasta 40 líneas sin contar blancos
  • Un archivo de lógica, hasta 400 líneas
  • Cero ciclos de importación
  • Se extrae un duplicado al tercer uso real

07

Personas y agentes, las mismas puertas

El arnés es lo que mantiene el trabajo dentro del producto. Personas y agentes leen los mismos documentos y cruzan las mismas puertas.

  • GOBERNANZA.md manda. Si una skill contradice la política, se aplica la política.
  • AGENTS.md, en la raíz y en cada proyecto, solo dice dónde está cada cosa.
  • CLAUDE.md fija cómo se lee el repositorio y qué ya está en pie.
  • ROADMAP.md es el plan de fases. Lo que no está en la fase abierta no se construye.

Las skills viven en .agents/skills, con espejo en .claude/skills y .github/skills, clavadas en skills-lock.json. Orientan el trabajo de hexágono, FHIR, seguridad, interfaz, duplicación y revisión de usabilidad. Cuando chocan, ceden: la capa externa se llama infrastructure; FHIR no promete recursos que el roadmap no pidió; la duplicación se extrae al tercer uso; en la interfaz manda impeccable, y sobre impeccable manda la gobernanza.

El diseño por spec es obligatorio cuando el cambio toca arquitectura, fronteras de módulo, el contrato REST o FHIR, la idempotencia, los roles o el tenant. El spec y el plan quedan en docs/superpowers.

  • Un agente no abre una fase que el roadmap no tiene abierta.
  • No apaga una regla ni un test para cruzar una puerta.
  • No toca secretos ni imprime credenciales.
  • No dice que algo funciona sin haber corrido el comando y visto la salida.
  • No hace commit ni push si nadie se lo pidió.

08

Una PR roja no entra

Cada cambio cruza las puertas en este orden. Si una falla, se arregla el código.

  1. 1
    Biome. biome ci en los dos proyectos.
  2. 2
    Tipos. tsc --noEmit en lo que se tocó.
  3. 3
    Vitest. Las suites del comportamiento afectado.
  4. 4
    React Doctor. Si el cambio mueve el frontend.
  5. 5
    OpenAPI. Si mueve /api/v1, se regenera el contrato y el cliente del frontend sigue sin edición manual. La suite contrato-api falla si el JSON quedó atrás o si hay una ruta sin declarar.
  6. 6
    Metadata. Si mueve FHIR, /fhir/metadata y las suites de conformidad van en la misma PR.
  7. 7
    Política. Si cambia una regla de trabajo, GOBERNANZA.md se actualiza en esa misma PR.

Las suites se nombran por lo que protegen.

  • fronteras el núcleo no importa framework, ORM ni node
  • contrato-api envoltura de error, request id y OpenAPI al día
  • roles 401 sin token, 404 entre tenants, alcance del widget
  • dominio tenant, cursor de paginación, ajustes, seed
  • aislamiento-tenant la base impide cruzar tenants
  • simetria-seed chatbot y simulador parten de los mismos datos
  • flujo el motor, los pasos y el chat por HTTP
  • verificacion par fijo, bloqueo y nada persistido
  • pre-agenda apartado atómico, tope y vencimiento
  • conocimiento-config bot-config, rotación de clave y búsqueda
  • alta-chatbot alta de tenant y tokens de plataforma
  • sesion-widget clave pública, origen y límite por IP
  • idempotencia repetir una escritura no la duplica
  • sin-ia ni dependencia ni import de modelo o n8n
  • fhir-conformance metadata y recursos, ni más ni menos
  • hermes-simulador el ciclo se cierra solo por FHIR
  • carga-basica latencia y límites con concurrencia moderada
  • cors orígenes del widget, alta y baja

Al cierre siguen en pie cuatro reglas de producto. El texto no sale de un modelo. Hermes es la fuente de verdad de la cita. Los mensajes, la auditoría y los logs no guardan respuestas de verificación ni datos clínicos. El simulador no viaja a producción.

09

FHIR es la puerta de Hermes

En fácil

FHIR R4 es el idioma en el que Hermes ya nombra pacientes, profesionales, agendas y citas. Este servicio traduce sus tablas a ese idioma. Hermes lee y escribe en /fhir sin conocer Postgres, el widget ni el motor de la conversación.

El paciente habla con el chatbot. El chatbot aparta un cupo y deja una solicitud. La cita en firme aparece cuando Hermes la escribe.

Los maestros son cinco recursos: paciente, profesional, servicio, agenda y cupo. Hermes los busca por un identificador de negocio, un par system|value. Si no hay coincidencia, se crea. Si hay una, se actualiza y conserva el id interno. Si hay más de una, no se escribe.

La pre-agenda usa otros dos recursos. Pedir cita o reprogramar se lee como un Appointment en estado proposed. Cancelar se lee como un Task en estado requested. Hermes responde escribiendo el estado final sobre el mismo id. booked confirma la cita. cancelled rechaza el pedido y libera el cupo. En una cancelación, completed anula la cita y rejected la deja como estaba.

Si el chatbot tiene el cupo apartado, Hermes solo puede marcarlo ocupado o no disponible. Esa escritura rechaza la solicitud en el mismo paso. Cambiar la hora, la agenda o devolver el cupo a libre espera a que el apartado venza o se resuelva.

Quien todavía no está en el padrón se lee como un Patient con la etiqueta pre-registered. Hermes lo confirma escribiendo el paciente real, sin esa etiqueta. El id interno sigue igual: la conversación y las solicitudes apuntan a la misma persona.

A /fhir entra el rol service. El panel y el widget siguen en /api/v1. Un id de otra clínica responde 404, igual que un id que no existe. GET /fhir/metadata es público y lista exactamente las operaciones que el servidor cumple.

Versión R4 4.0.1, solo JSON. El equipo de Hermes lo confirmó el 14 de octubre de 2026. Los perfiles viven en este repositorio: metadata es el contrato que se puede leer.
Dos escrituras Los maestros se crean o actualizan con un PUT que busca por identificador. La pre-agenda se resuelve con un PUT al id de la solicitud.
Quién manda Hermes confirma, reprograma y cancela. El chatbot origina la solicitud y el pre-registro. Ocupar un cupo apartado rechaza esa solicitud; no confirma una cita.
Repetir Toda escritura lleva Idempotency-Key. La misma petición devuelve el mismo resultado y no abre un segundo registro.

El contrato

El módulo modules/fhir tiene domain y application. Declara puertos de lectura y de escritura. composition/fhir-wiring.ts los cumple con scheduling y patients. fhir no importa esos módulos; la suite fronteras cierra el corte. La versión, el MIME, los systems, los tags y los value sets están solo en profiles.ts.

Hay una ruta, app/fhir/[[...path]]. El despacho consulta registry.ts, y de ese mismo registro sale el CapabilityStatement. Añadir un recurso o un parámetro de búsqueda es declararlo ahí. metadata no se edita a mano. fhir-conformance recorre lo declarado y exige un valor de muestra por parámetro.

fhir-route.ts no importa errors.ts. Toda respuesta, también el fallo, lleva Content-Type: application/fhir+json y X-Request-Id. El cuerpo de error es un OperationOutcome.

Lectura. read es GET /fhir/{Tipo}/{id}. search-type es GET /fhir/{Tipo}. Se leen los siete tipos. El id de la URL es el id interno. El identificador de Hermes viaja en identifier.

Patient Expediente. Dos identifier: el de negocio y el documento (urn:ingenius:document:{CC|TI|CE|PA|RC}). Si el estado es pre_registered, lleva meta.tag urn:ingenius:patient-tag|pre-registered. Búsqueda: identifier, _tag.
Practitioner Identificador, nombre, active. Búsqueda: identifier, active.
HealthcareService Identificador, nombre, active. Misma búsqueda que el profesional.
Schedule Identificador, active y actor al profesional y al servicio. Búsqueda: identifier, actor, active.
Slot Agenda, estado, inicio y fin. busy_tentative sale como busy-tentative y busy_unavailable como busy-unavailable. Búsqueda: identifier, schedule, status, start.
Appointment Cita en firme (booked, cancelled, fulfilled, noshow) o solicitud de alta o reprogramación. La pendiente es proposed, con identificador urn:ingenius:appointment-request|{id}. La rechazada o vencida se lee cancelled. Búsqueda: identifier, patient, slot, status, date.
Task Solo solicitudes de cancelación. intent fijo proposal. Viva requested, aprobada completed, rechazada rejected, vencida cancelled. focus es la cita que se cancela y for es el paciente. Búsqueda: identifier, status, focus, patient.

identifier exige system|value. El valor a solas responde 400 invalid. Las referencias son relativas (Patient/{id}, Schedule/{id}). actor acepta profesional o servicio. start y date aceptan eq, ge, gt, le y lt, y se repiten para formar un rango. Con offset se usan tal cual. Una fecha sin hora es el día completo en APP_TIMEZONE.

_count vale 50 si no viene; por encima de 200 se recorta a 200. _offset parte de 0. Un valor mal formado responde 400. El Bundle es searchset, con total y enlaces self, next y previous. Cada entrada lleva fullUrl y search.mode = match. Maestros y Patient se ordenan por id. Slot y Appointment se ordenan por inicio y luego por id. Task se ordena por el inicio de la cita que cancela.

Un parámetro que el registro no declara para ese tipo responde 400 not-supported. Varios parámetros se combinan con AND. El tenant de toda consulta es el claim del token. Filtrar por una referencia de otro tenant devuelve un conjunto vacío. Antes de leer Slot, Appointment o Task se vencen las solicitudes vencidas de ese tenant: el cupo vuelve a free y la solicitud deja de salir como proposed o requested.

Escritura de maestros. Solo PUT /fhir/{Tipo}?identifier=system|value, con un segmento, para los cinco tipos. PUT /fhir/Patient/{id} responde 405. En metadata esos cinco declaran update con conditionalUpdate: true y updateCreate: false, y un texto que limita el verbo al condicional. El id lo asigna el servidor.

El orden es rol, ruta, tipo de contenido, clave y cuerpo. Se acepta application/fhir+json y application/json. Otro tipo responde 415 not-supported, sin leer el cuerpo. La Idempotency-Key es obligatoria, de al menos un carácter, y comparte el almacén de REST. El hash incluye método, ruta, query y cuerpo. La misma clave con el mismo hash repite el 201 o el 200 guardados. La misma clave con otro cuerpo o con otra query responde 409. Un rechazo revierte la transacción y no guarda la clave.

Cero coincidencias crea (201). Una actualiza y conserva el id (200). Más de una responde 412 multiple-matches y no escribe. El id del cuerpo puede faltar. Si viene y no es el del recurso encontrado, o si no hay coincidencia y el cuerpo trae id, la respuesta es 400 invalid. El identificador de la query tiene que estar en el cuerpo, y resourceType tiene que coincidir con la ruta. Location apunta a /{Tipo}/{id}.

Se ignoran meta, text, use y extension. Un elemento con significado que no se persiste, o un modifierExtension, responde 422 structure. Un campo obligatorio ausente, un value set inválido o un start que no es anterior a end responde 422 processing. R4 separa el JSON que no se puede leer (400) del recurso que se leyó y el servidor rechaza (422).

En Patient, el system de negocio lo elige Hermes: no es un system de documento ni urn:ingenius:pre-registration. Si ese documento pertenece a un expediente pre_registered del tenant, el PUT confirma ese expediente: mismo id, identificador del cuerpo, estado active, y el tag deja de salir. Si el documento ya es de un paciente activo, 409. Mandar el tag pre-registered en el cuerpo responde 422 business-rule.

Schedule.actor y Slot.schedule usan el id interno. Si el profesional, el servicio o la agenda no existen en el tenant, responde 422 processing y no crea la fila. En un Slot apartado por una solicitud pendiente, el único estado aceptado es busy o busy-unavailable. El cupo queda así y la solicitud pasa a rejected con motivo slot_unavailable, en la misma transacción. Otro cambio responde 409 y deja el apartado intacto. Un cupo sin solicitud pendiente acepta el estado del cuerpo. Los índices únicos de identificador y de documento cierran la carrera: una violación sale como 409, no como 500.

Cada escritura aplicada deja auditoría con actor service, acción patient.written_by_hermes (y el equivalente de profesional, servicio, agenda y cupo) y el id del recurso. El cuerpo no se guarda. El rechazo del apartado añade appointment_request.rejected.

Pre-agenda. PUT /fhir/Appointment/{id} y PUT /fhir/Task/{id}. El PUT condicional de estos dos tipos responde 405. En metadata declaran update con conditionalUpdate: false y updateCreate: false. El id del recurso es el id de la solicitud. Al aprobar un alta o una reprogramación, la cita en firme se inserta con ese mismo id. El cuerpo booked trae el identificador de negocio de la cita, distinto de urn:ingenius:appointment-request.

Appointment.replaces no existe en R4. La reprogramación lleva la extensión http://hl7.org/fhir/5.0/StructureDefinition/extension-Appointment.replaces con valueReference a la cita que sustituye. Solo sale en reschedule, y el literal vive en profiles.ts. En proposed, el paciente va accepted y el profesional y el servicio van needs-action. En la cita en firme, los tres van accepted. El motivo de resolución va en statusReason, system urn:ingenius:resolution-reason: slot_unavailable si el cuerpo trae ese código; si no, declined.

  1. 1
    Appointment booked. Aprueba un alta o una reprogramación viva. Responde 200 con la cita booked y el identificador del cuerpo.
  2. 2
    Appointment cancelled. Rechaza esa solicitud y libera el cupo. Responde 200 con la cita cancelled.
  3. 3
    Task completed. Aprueba la cancelación: la cita pasa a cancelled y su cupo a free.
  4. 4
    Task rejected. Rechaza la cancelación. La cita en firme no cambia.

Otro status responde 422 processing. El id del cuerpo puede faltar; si viene y no es el de la URL, 400. Una query en el PUT por id responde 400 not-supported. intent puede faltar; si viene y no es proposal, 422. Una solicitud que ya no está pendiente, o una cita en firme, responde 409 conflict. Un id desconocido o de otro tenant responde 404. La aprobada no se duplica en la lectura: la representa la cita en firme. Cada PUT aplicado suma appointment.written_by_hermes o task.written_by_hermes, además del evento de la resolución.

El fallo, en los dos verbos, sigue esta tabla.

  • 401 login sin token, o token inválido
  • 403 forbidden rol distinto de service
  • 404 not-found tipo o id desconocido, u otro tenant
  • 405 not-supported verbo o forma de PUT que el tipo no declara
  • 415 not-supported Content-Type distinto de fhir+json o json
  • 400 invalid JSON, query, resourceType o id del cuerpo
  • 422 structure elemento no persistido o modifierExtension
  • 422 processing campo, value set, referencia o estado no resoluble
  • 422 business-rule tag pre-registered en el cuerpo
  • 409 conflict clave reutilizada, documento ajeno, cupo apartado, ya resuelto
  • 412 multiple-matches más de un recurso con ese identifier
  • 500 exception fallo no previsto

metadata declara read y search-type en los siete tipos, update condicional en los cinco maestros y update por id en Appointment y Task. También documenta que las escrituras exigen Idempotency-Key, una cabecera de este servidor. Quedan fuera del registro vread, history, _include, _revinclude, _sort, _summary, POST _search, PATCH, el borrado, If-Match y las versiones. La fecha del contrato, CAPABILITY_DATE, cambia cuando cambia lo declarado.
